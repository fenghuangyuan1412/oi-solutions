### 1.3 第 16 行 `int i = 2` → `int i = 1`（`r1_i1.exe`）

| n | 原版输出 | 改版输出 | 原版和 | 改版和 |
|---|---|---|---|---|
| 14 | `3 5 / 5 7 / 11 13` | **`1 3`** ` / 3 5 / 5 7 / 11 13` | 44 | **48** |
| 50 | 6 对 | **多一行 `1 3`**，共 7 对 | 224 | **228** |

原因：`isPrime(1)` **返回 true**（`ip1.exe`）：

```

isPrime(2) = true        isPrime(3) = true
```
`for(int i = 2; i < 1; ++i)` 一次都不进入循环，直接落到 `return true;`。
所以 `i=1` 时 `isPrime(1) && isPrime(3)` 为真，凭空多打印一行 `1 3` → 第 17 题 **F** ✅
（注意：这个"1 也是质数"的漏洞真实存在，是 18 题之外很好的讲课点。）

## 3. 第 3 篇（dfs + 1e9，r3.cpp）

### 3.0 这个程序到底在算什么（先给结论）

状态是一个长 `n+1` 的 01 串 `t`（下标 0..n）。
"翻第 i 位"合法的充要条件：**`t` 的前 i 个字符 == `s` 的后 i 个字符**（i=0 时空串等于空串，恒合法）。
目标：从 `t = 00…0` 出发，用最少的翻转次数到达 `t = 11…1`（`ret==0` 的判据就是"每一位都是 '1'"）。
走不到就返回 `1e9`。`i != lst` 用来禁止"刚翻这一位又翻回去"的无用动作。

这就是**九连环（Chinese Rings）式的翻转链**：`s` 决定"解锁第 i 环需要的构型"，
合法的无回头路状态转移恰好把 2^(n+1) 个状态串成一条 **Gray 码式的路径**，
所以 `dfs` 沿这条路径一条道走到底，答案 = 全 1 状态在这条路径上的**下标**。
（实测：`11…1`（n=8）→ 9 = n+1；`00000001` → 341 = (2¹⁰−1)/3。）

**重要环境事实**：`n≤18` 时递归深度上界是 2¹⁹−1 = 524287（实测这两份 n=18 输入深度都是 289745），
**默认 8MB 栈直接爆栈，程序没有任何输出**（实测栈需 32~64MB 之间才跑得动）。
本机数据：

| 链接参数 | `110111011110111110` 的结果 |
|---|---|
| `--stack,8388608`（8MB，评测机默认） | 崩溃，无输出，bash 返回 127 |
| `--stack,16777216` / `33554432` | 崩溃，无输出 |
| `--stack,67108864`（64MB） | 正常输出 **289745**，耗时 ≈1s |
| `--stack,1073741824`（1GB） | 正常输出 289745，耗时 1~2s |

下面所有 n=18 的数字都是用大栈版本（`r3_big.exe` / `r3_var_big.exe`）跑出来的，
并且用一份**完全独立的位压缩 BFS**（`r3_bfs.exe`）复核过答案，两者逐个相同。

### 3.2 第 31 题：`110111011110111110` 的 dfs 调用次数

```
[answer]=289745   [calls]=524288   [distinct states]=524288   [max depth]=289745
```
- 真实调用次数 = **524288 = 2¹⁹**（正好等于全部 2^(n+1) 个状态，说明搜索是一条 Hamilton 路径）。
- 官方答案是 B"219"。**这里不是官方错，是 PDF→TXT 丢了上标**：
  卷面选项原本是 A. 2¹⁸ B. 2¹⁹ C. 2²⁰ D. ABC 均错，提取后变成"218 / 219 / 220"。
  同一份文本里还有两处同样的痕迹：完善程序(1) 题干的 `1 ≤ k ≤ n ≤ 105`（=10⁵）、

  而 2¹⁹=524288 与实测完全吻合 → **B（=2¹⁹）正确** ✅

### 3.6 第 28 题：删掉 `i != lst &&`

`r3_var.exe 4`（默认栈）：

| 输入 | 结果 |
|---|---|
| `1` | 崩溃，无输出（rc=127） |
| `11` / `01` / `11111111` / `00000001` / `10011101010` | 全部崩溃，无输出 |

原因：`i=0` 的条件恒为真（见 §3.8），所以任何状态都能翻第 0 位；

具体改变的例子：**输入只要一个 `1`，原本输出 2，改后直接运行时错误** → **F** ✅

### 3.7 第 29 题 C 选项：`cur[i] ^= 1;` → `cur[i] = 'a' - cur[i];`

`r3_bits.exe` 实测 ASCII：
```
'0'(=48):  ^=1  -> '1'(49) ;  'a'-'0' -> '1'(49) ;  相等? YES
'1'(=49):  ^=1  -> '0'(48) ;  'a'-'1' -> '0'(48) ;  相等? YES
```
`t` 里只可能出现 '0' 和 '1'（初值全 '0'，每步只翻一位），
而 48^1=49、49^1=48，97−48=49、97−49=48 —— **两种写法逐点等价，输出完全不变**
（`r3_var.exe 8` 对 §3.4 五组输入实测与原版全同）→ C 说法错 ✅

顺带：第 29 题 B 选项"存在输入使程序自然溢出"为假：
`dfs` 的返回值上界是 `1e9 + 18`（不可达时返回 1e9，逐层 +1 最多 18 层，`min` 会把它压回 1e9），
远小于 INT_MAX=2147483647；穷举 n≤12 实测可达答案最大 5461。
→ A、B、C 全错 → 第 29 题 **D** ✅

### 3.8 `i = 0` 时 `s.substr(n-i,i) == t.substr(0,i)` 是否恒真

```
s.size()=8, s.substr(n-0,0) = "" (长度0)
t.substr(0,0)               = "" (长度0)
穷举 2^9 个 t 验证 i=0 条件为假的个数 = 0
```
**恒为真**（注意 `s.substr(n,0)` 中 pos == size() 是合法的，返回空串，不会抛 out_of_range）。
这条决定了搜索图的形状：**第 0 位在任何时刻都允许翻**（只被 `i != lst` 拦一下），
所以图上每个点都有一条"翻第 0 位"的出边 —— 这也是 3.6 里去掉 guard 就立刻死循环的根本原因。

### 3.9 第 18 问（栈溢出 / int 溢出）

- **int：不会自然溢出**。见 §3.7，上界 1e9+18。
- **栈：会溢出。** n=18 时递归深度实测 289745，每帧约 120 字节（两个 `std::string` 形参/局部量），
  需要 ≈35MB 栈，超过评测机默认的 8MB → 直接 RE。
  实测阈值：8/16/32MB 全崩，64MB 通过（1~2 秒）。
- 时间：calls 上界 2¹⁹ = 524288 次，n=18 也只要 1~2 秒，**不会 TLE，会 RE**。
  → 严格来说，第 31、32 题这两个 n=18 输入在正常环境下"程序没有输出"，
    讲课时应说明"答案是理论值（把栈开大后实测）"。

## 4. 完善程序(1) 序列第 k 小（fill1.cpp，33~37 = A C D D A）

```cpp
bool check(int x) { int c = 0;
    for (int i = 1; i <= n; i++) if (a[i] <= x) c++;      // ① A
    return k <= c; }                                       // ② C
int main() { ... int l = 1, r = 2e9;                       // ③ D
    while (l < r) { int x = l + (r - l) / 2;               // ④ D
        if (check(x)) r = x; else l = x + 1; }             // ⑤ A
    cout << l << endl; }
```

`fill1.exe` 手工样例：

| 输入 | 输出 | 正确 |
|---|---|---|
| `5 3 / 7 2 9 1 5` | 5 | ✅ |
| `5 1 / 7 2 9 1 5` | 1 | ✅ |
| `5 5 / 7 2 9 1 5` | 9 | ✅ |
| `3 2 / 2000000000 1 2000000000` | 2000000000 | ✅ |

`fill1_stress.exe`（**5000 组随机对拍**，n≤50，1≤a[i]≤2×10⁹，与 `sort` 后第 k 小比较）：

```
④填D：与 sort 结果不一致 = 0 / 5000        <-- 官方答案正确
④填A：与 sort 结果不一致 = 2316 / 5000  （全部是死循环，被迭代上限强行截断）
```

关于 **③ 填 `2e9` 有没有 int 溢出隐患**（实测）：

```
INT_MAX = 2147483647 ; (double)2e9 = 2000000000 ; int r = 2e9 -> r = 2000000000
   ==> 2e9 是 double 字面量，转成 int 得 2000000000 < INT_MAX，本身不溢出
   ==> 补充实测：g++ 13.1 加 -Wall 编译 `int r = 2e9;` 没有任何警告；
       只有 `int r = 2.2e9;`（真的超出 INT_MAX）才报
       warning: overflow in conversion from 'double' to 'int' changes value
       from '2.2e+9' to '2147483647' [-Woverflow]，且程序输出 2147483647。
       所以不能指望编译器替学生发现这类转换。
1 << 32 = 1（本机实测，移位 >=32 位是未定义行为） ; 1 << 31 = -2147483648（有符号溢出 UB）
   ==> ③ 的 C 选项 1<<32 不但错，而且是"看起来像对"的 UB
```
真正有溢出隐患的是 **④**：`l` 和 `r` 都可能取到 2×10⁹ 量级，`(l + r)` 最大约 4×10⁹ ≫ INT_MAX。
实测三组极端数据：

```
n=5 k=1 a={2e9,2e9,2e9,2e9,2e9}        正确=2000000000 : D->2000000000  A->死循环(迭代201次被截断)
n=5 k=5 a={1,2,3,2e9,1999999999}       正确=2000000000 : D->2000000000  A->死循环
n=4 k=4 a={1.5e9,1.6e9,1.7e9,2e9}      正确=2000000000 : D->2000000000  A->死循环
```
→ **③ 用 2e9 安全；④ 必须写 `l + (r - l) / 2`，写 `(l+r)/2` 在数据接近 2×10⁹ 时会溢出并死循环。**

其它空填错的后果（同一程序实测）：

| 填法 | 数据 `a={7,2,9,1,5} k=3`（正确 5） | 结果 |
|---|---|---|
| ③ 填 C `1<<32` | r 变成 1，二分根本不跑 | 输出 **1** ❌ |
| ③ 填 B `a[n]` | `a={5,1,9,2,3}` 时 a[n]=3 < 真答案 5 | 输出 **3** ❌ |
| ② 填 A `c <= k` | 二分方向反了 | 输出 **2000000000** ❌ |
| ① 填 B `a[i] < x` | 严格小于 → 找到的是"第 k+1 小" | 输出 **6** ❌（off-by-one） |
| ④ 填 C `l + (r - l) >> 1` | 优先级：`>>` 低于 `+`，整体变成 `r >> 1` | 逻辑完全错 ❌ |

## 附：题面与 PDF 的交叉核对（凭什么可以相信 problem.txt）

用户提供的卷子是 PDF，仓库里存的是 `problem.txt`（人抄一遍、中文保留完整）。
为了确认"抄的这份就是卷子本身"，做了四道核对：

| 核对 | 做法 | 结果 |
|---|---|---|
| ① 答案表 | 卷面最后几页的参考答案逐题与本目录实测结论比对 | J 42 题、S 43 题**全部一致**，没有任何一题被实测证伪 |
| ② 程序可编译 | `problem.txt` 里每段程序单独抽出来 `g++ -static -O2 -std=c++14` 编译 | 全部通过（缺一个括号、错一个下标都过不了） |
| ③ 行号连续性 | 脚本扫 `paper.md` 的每个代码块，检查行号是不是 $1..N$ 连续无缺 | J 8 个代码块、S 5 个代码块，**无一缺号、无一跳号** |
| ④ 与 pdftotext 对撞 | 同一份 PDF 用 `pdftotext -layout` 再导一份纯文本逐行比 | 差异**全在排版层**，见下 |

第 ④ 条的具体差异类型（这些都不算内容差异）：

1. **pdftotext 丢掉全部中文**（导出环境缺 CMap），所以它只能用来核对代码，题面必须以 `problem.txt` 为准。
2. **分栏与字距**：选项被挤成一行（`A. 28  B. 30  C. 25  D. 27`）、缩进空格数不同。
3. **行号归属错位**：两条文字基线在 PDF 里挨得太近时，pdftotext 会把它们并成一行。
   例如选择题 3 那个"双栈模拟队列"的程序（25 行），pdftotext 读作
   `22:(空) / 23:} / 24:} / 25:} return 0;`，`problem.txt` 读作
   `22:} / 23:} / 24:return 0; / 25:}`。两者的字符完全一样，只是行号分配不同 ——
   而**只有 problem.txt 这个排列能编译** —— 把两行对调后本机
   `g++ -static -O2 -std=c++14` 直接报
   `t_p25b.cpp:25:5: error: expected unqualified-id before 'return'`，
   且它跑出来的输出与卷面答案一致。

⇒ 结论：凡是两边冲突的地方，`problem.txt` 既能编译又能复现卷面答案，以它为准。
